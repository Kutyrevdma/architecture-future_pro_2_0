# Задание 4. Проектирование событийной модели и доменных границ

## 1. Цель задания

Целью данного задания является проектирование доменной модели и событийной архитектуры для платформы компании «Будущее 2.0».

В рамках работы необходимо:

* определить ключевые домены системы;
* выделить границы bounded context;
* определить основные агрегаты доменной модели;
* описать каталог доменных событий;
* показать основной бизнес-процесс через Event Storming.

Проектирование выполнено с использованием подходов **Domain Driven Design (DDD)** и **Event-Driven Architecture**.

---

# 2. Архитектурные принципы

При проектировании архитектуры были использованы следующие принципы.

### Domain Driven Design

Каждый бизнес-домен обладает:

* собственными агрегатами
* собственными моделями данных
* собственными событиями

Это позволяет уменьшить связанность между сервисами и обеспечить независимое развитие доменов.

### Event-Driven Architecture

Взаимодействие доменов осуществляется через события, публикуемые в брокере сообщений.

Основные преимущества:

* слабая связанность сервисов
* возможность горизонтального масштабирования
* near-real-time обработка данных
* упрощённая интеграция новых систем

---

# 3. Границы доменов (Bounded Contexts)

В архитектуре платформы выделены следующие доменные контексты:

| Контекст               | Назначение                                          |
| ---------------------- | --------------------------------------------------- |
| Customer Context       | управление клиентами системы                        |
| Medical Context        | управление пациентами и медицинскими процессами     |
| AI Diagnostics Context | анализ медицинских исследований с использованием ИИ |
| Fintech Context        | банковские сервисы и финансовые операции            |
| Billing Context        | выставление счетов за услуги                        |
| Inventory Context      | управление медицинскими расходными материалами      |
| Staff Context          | управление персоналом клиник                        |


Файл диаграммы:

```
bounded-contexts.puml
```

---

# 4. Основные агрегаты

Каждый доменный контекст содержит агрегаты, инкапсулирующие бизнес-логику.

### Customer Context

**Customer**

Описание: клиент компании, который может использовать медицинские и финансовые сервисы.

Ключевые события:

* CustomerRegistered
* CustomerUpdated

---

### Medical Context

Основные агрегаты:

* Patient
* Appointment
* Diagnosis
* ImagingStudy

Ключевые события:

* PatientCreated
* AppointmentScheduled
* AppointmentCompleted
* DiagnosisRecorded
* ImagingStudyRequested
* ImagingStudyCompleted

---

### AI Diagnostics Context

**AIAnalysis**

Описание: анализ медицинских исследований алгоритмами искусственного интеллекта.

События:

* AIAnalysisRequested
* AIAnalysisCompleted

---

### Fintech Context

Агрегаты:

* Account
* Loan

События:

* AccountOpened
* LoanApplicationSubmitted
* LoanApproved
* LoanDisbursed

---

### Billing Context

**Invoice**

Описание: счёт за оказанные медицинские услуги.

События:

* InvoiceCreated
* PaymentReceived

---

### Inventory Context

**InventoryItem**

Описание: расходные материалы медицинского учреждения.

События:

* InventoryItemUsed
* InventoryLow

---

### Staff Context

**StaffMember**

Описание: сотрудник медицинского учреждения.

События:

* StaffAssigned
* StaffLeft

---

# 5. Каталог доменных событий

Все ключевые изменения состояния системы публикуются как доменные события.

Каталог событий представлен в файле:

```
events.md
```

События используются для:

* интеграции доменов
* построения аналитики
* запуска асинхронных процессов

---

# 6. Event Storming

Event Storming используется для моделирования бизнес-процессов и выявления ключевых событий системы.

Диаграмма демонстрирует основной сценарий взаимодействия доменов:

1. регистрация клиента
2. создание пациента
3. запись на приём
4. проведение диагностики
5. анализ данных ИИ
6. выставление счёта
7. оплата услуги

Файл диаграммы:

```
event-storming.puml
```

---

# 7. Связь событий и агрегатов

Агрегаты генерируют события при изменении своего состояния.

Пример цепочки событий:

```
AppointmentCompleted
   ↓
DiagnosisRecorded
   ↓
ImagingStudyRequested
   ↓
ImagingStudyCompleted
   ↓
AIAnalysisRequested
   ↓
AIAnalysisCompleted
   ↓
InvoiceCreated
   ↓
PaymentReceived
```

Такая модель позволяет строить реактивные бизнес-процессы и обеспечивает независимое развитие доменов.
