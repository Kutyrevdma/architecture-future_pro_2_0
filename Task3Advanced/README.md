# Задание 3. Проектирование целевой архитектуры и оценка рисков внедрения

## 1. Целевая архитектура системы «Будущее 2.0» в горизонте трёх лет

### 1.1 Диаграмма контейнеров в нотации C4

Целевая архитектура аналитической платформы компании «Будущее 2.0» строится на принципах событийной архитектуры и доменной ответственности за данные. Основная цель архитектуры — обеспечить масштабируемую платформу аналитики и самообслуживания для сотрудников компании, а также создать основу для интеграции новых бизнес‑направлений и источников данных.

Архитектура ориентирована на переход от централизованного DWH к распределённой модели данных, где каждый домен владеет своими данными и публикует дата‑продукты для аналитики.

Ключевые элементы архитектуры:

* **Self‑Service Portal** — единый интерфейс для бизнес‑пользователей, позволяющий находить наборы данных, строить отчёты и проводить анализ.
* **API Layer** — API‑шлюз, через который осуществляется доступ к аналитическим сервисам.
* **Event Bus (Kafka)** — событийная платформа, обеспечивающая обмен событиями между доменами.
* **Domain Services** — сервисы доменов, реализующие бизнес‑логику и публикующие события.
* **Domain Storage** — операционные базы данных доменов.
* **Domain Data Products** — аналитические наборы данных, подготовленные доменами.
* **Analytical Storage (S3 + Iceberg)** — хранилище аналитических данных.
* **Query Engine (Trino)** — SQL‑движок для доступа к аналитическим данным.
* **Metadata Service (DataHub)** — каталог данных и метаданных.
* **Workflow Scheduler (Airflow)** — система оркестрации пайплайнов обработки данных.
* **Access Management (Keycloak)** — централизованная система аутентификации и авторизации.
* **Analytics Tools (Superset / Tableau)** — инструменты визуализации и построения дашбордов.

Legacy‑системы (SQL Server DWH и интеграционная шина Apache Camel) используются как слой совместимости в процессе миграции.

### 1.2 Изменения ключевых систем при масштабировании

| Существующая система         | Целевое состояние                                     | Изменения и обоснование                                              |
| ---------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------- |
| DWH (SQL Server 2008)        | Постепенно выводится из эксплуатации                  | Аналитическая нагрузка переносится в Data Lakehouse (S3 + Iceberg).  |
| Power BI                     | Используется совместно с новым аналитическим порталом | BI‑инструменты получают доступ к данным через Trino.                 |
| ESB (Apache Camel)           | Временный слой интеграции                             | Постепенно заменяется событийной архитектурой на базе Kafka.         |
| Финтех‑сервисы               | Декомпозиция на доменные микросервисы                 | Каждый сервис получает собственную базу данных и публикует события.  |
| ИИ‑сервисы                   | Интеграция через события                              | Результаты обработки публикуются в Kafka и используются в аналитике. |
| Медицинская система          | Постепенная модернизация                              | Функциональность переносится в новые сервисы.                        |
| Отсутствие портала аналитики | Появляется Self‑Service портал                        | Пользователи могут самостоятельно формировать отчёты.                |

### Новые бизнес‑направления

При расширении экосистемы компании (например, интеграция фармацевтических компаний или производителей медицинского оборудования) новые участники подключаются как отдельные домены. Каждый домен публикует события в Kafka и предоставляет собственные дата‑продукты для аналитики.

### Интеграция новых источников данных

Интеграция внешних источников данных (например, медицинские устройства, партнерские системы, внешние API) осуществляется через адаптеры и коннекторы. Эти данные преобразуются в события и публикуются в Kafka.

## 2. Карта рисков трансформации

| Риск                                   | Категория       | Вероятность | Влияние | Пояснение                                                                 |
| -------------------------------------- | --------------- | ----------- | ------- | ------------------------------------------------------------------------- |
| Потеря данных при миграции             | Технологический | Средняя     | Высокое | Возможны ошибки при переносе исторических данных.                         |
| Несогласованность схем событий         | Архитектурный   | Средняя     | Среднее | Домены могут использовать разные структуры событий.                       |
| Сложность управления доступом          | Архитектурный   | Высокая     | Высокое | Распределённая архитектура требует более сложных механизмов безопасности. |
| Недостаточная производительность Kafka | Технологический | Низкая      | Среднее | При росте числа событий может потребоваться масштабирование.              |
| Сопротивление сотрудников изменениям   | Организационный | Высокая     | Среднее | Пользователи привыкли к старым инструментам отчётности.                   |
| Параллельная поддержка старых систем   | Организационный | Средняя     | Высокое | На этапе миграции потребуется поддерживать несколько архитектур.          |
| Нарушение регуляторных требований      | Организационный | Низкая      | Высокое | Медицинские и финансовые данные требуют строгого контроля.                |
| Отсутствие стандартов дата‑продуктов   | Архитектурный   | Средняя     | Среднее | Домены могут создавать несовместимые наборы данных.                       |
| Низкая производительность аналитики    | Технологический | Средняя     | Среднее | Большие объёмы данных требуют оптимизации хранения.                       |
| Vendor lock‑in                         | Технологический | Низкая      | Среднее | Использование облачных сервисов может ограничить переносимость.           |

## 3. План управления рисками

### 3.1 Технические меры

| Риск                         | Меры                                                                    |
| ---------------------------- | ----------------------------------------------------------------------- |
| Потеря данных                | Резервное копирование, проверка целостности данных, поэтапная миграция. |
| Несогласованность схем       | Использование Schema Registry и форматов Avro или Protobuf.             |
| Управление доступом          | Централизованный IAM (Keycloak), разграничение доступа по ролям.        |
| Производительность Kafka     | Масштабирование кластера, мониторинг нагрузки.                          |
| Регуляторные требования      | Шифрование данных, аудит доступа.                                       |
| Стандарты дата‑продуктов     | Внедрение Data Catalog (DataHub).                                       |
| Производительность аналитики | Использование Parquet, партиционирование данных.                        |
| Vendor lock‑in               | Использование Kubernetes и открытых технологий.                         |

### 3.2 Управленческие меры

| Риск                      | Меры                                                        |
| ------------------------- | ----------------------------------------------------------- |
| Сопротивление сотрудников | Проведение обучения и демонстраций новой системы аналитики. |
| Задержки проекта          | Реализация проекта поэтапно и запуск пилотных доменов.      |
| Регуляторные риски        | Вовлечение специалистов по комплаенсу и проведение аудитов. |
